# Open-source agent memory & knowledge-base systems: mechanism-level comparison (as of 2026-10-31)

Scope: Letta (MemGPT), mem0, Zep/Graphiti, Cognee, LangMem; memory designs inside coding agents (Claude Code auto memory, Cursor rules/memories, Cline memory bank, Aider repo map, Codex memory + AGENTS.md, Letta Code MemFS); 2026 research (A-MEM, MemoryBank, CoALA taxonomy, Voyager-style skill libraries, provenance-aware memory, staleness benchmarks). Target use: a team-facing AI engineer's knowledge base with typed items, provenance, human verification, staleness detection, distillation at ticket close, retrieval at ticket start, Confluence publishing.

Source-quality note: Official docs and arXiv abstracts were fetched directly where possible. Several Graphiti/Letta doc pages 404'd or reset during fetch; for those I relied on the GitHub README, the Zep engineering blog, or clearly marked secondary write-ups. Benchmark claims are vendor-reported unless noted and are contested (see Q5).

## Q1. Per-system mechanism comparison (memory model, storage, write policy, consolidation, retrieval, invalidation, provenance, scopes, cost, APIs)

### Takeaway
The field has converged on a small number of mechanisms: (a) an always-in-context "core" block plus searchable long-term store (Letta); (b) LLM-driven fact extraction with ADD/UPDATE/DELETE decisions over a vector store (mem0, LangMem); (c) temporal knowledge graphs where contradictions invalidate edges instead of overwriting (Graphiti/Zep, Hindsight, Agent Zero); and (d) plain markdown files in a repo curated by the agent itself (Claude Code auto memory, Cline memory bank, Letta MemFS, Codex memories, Karpathy's "LLM wiki"). Coding agents overwhelmingly chose (d); conversational-memory vendors chose (b)/(c).

### Cited Findings

**Letta (MemGPT lineage)**
- Three-tier model: "Important 'core' memories are injected into the context window of the LLM, and the agent can modify its own memories through tools"; "all state, includes memories, user messages, reasoning, tool calls, are all persisted in a database, so they are never lost, even once evicted from the context window." — [Letta docs: memory](https://docs.letta.com/guides/agents/memory)
- Memory blocks have fields `label`, `description`, `value`, `limit` (character cap) and `read_only`; blocks are "always visible - no retrieval needed" and rendered as XML-like sections prepended to the LLM context. Multiple agents can attach the same persisted block ("update once, visible everywhere"); `read_only: true` is suggested for "shared memory block[s] about an organization". Direct value updates "completely replace the entire block content" with "last write wins" under concurrency. — [Letta docs: memory blocks](https://docs.letta.com/guides/agents/memory-blocks)
- Archival memory is long-term vector storage backed by PostgreSQL (pgvector), SQLite, optionally Pinecone/Turbopuffer, searched via an `archival_memory_search` tool; a sleep-time agent "consolidates memory asynchronously while the primary agent is idle" and can "consolidate or invalidate archival records." — [learn.traeai.com (secondary summary)](https://learn.traeai.com/t/ai-engineering/phases/14-agent-engineering/08-memory-blocks-sleep-time-compute.html); [Letta forum: sleeptime best-practices](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154)
- Letta Code (2026) replaced memory blocks with **MemFS**: "a git-backed memory filesystem that they can inspect and edit." `/init` bootstraps project memory, `/remember` teaches explicit lessons, and the agent "decides where the lesson belongs and commits the update to MemFS." "Dreaming uses background subagents to review recent conversations, consolidate useful lessons, and update memory without interrupting your active work", triggered "after a set number of completed agent steps or when the context window is compacted", with an optional "Agent reviews before applying" second pass that "uses more model tokens". Limits: 5 MiB/repo (free), 50 MiB (Pro). — [Letta Code memory docs](https://docs.letta.com/letta-code/memory)
- MemFS lives at `~/.letta/agents/<agent-id>/memory` as a standard git repo; "Every memory edit is tracked in git history with an informative commit message"; the agent must commit and push for edits to take effect; "Memory subagents (such as the reflection and defrag subagents) use git worktrees so they can write to memory concurrently"; "MemFS replaces memory blocks for agents on the Letta API." — [search summary of docs.letta.com/letta-code/memfs](https://docs.letta.com/letta-code/memfs) (page itself returned 404/ECONNRESET on fetch; treat details as unverified beyond the search snippet)

**mem0**
- Paper (arXiv 2504.19413, submitted 2025-04-28): extraction + consolidation phases with four operations ADD, UPDATE, DELETE, NOOP; graph variant Mem0g gives ~2% over base; claims 26% relative LLM-as-judge improvement over OpenAI memory on LoCoMo, 91% lower p95 latency and 90% token savings vs full-context. — [arXiv 2504.19413](https://arxiv.org/abs/2504.19413)
- Current docs describe `add()` as: "Mem0 sends the messages through an LLM that pulls out key facts, decisions, or preferences to remember", and an **"ADD-only" model where "new memories are added without overwriting or deleting existing memories"** (this contradicts the 2025 paper's UPDATE/DELETE operations — the 2026 algorithm appears to have changed write policy). `infer=False` "stores your payload exactly as provided, so duplicates can land." Scopes: `user_id`, `agent_id`, `app_id`, `run_id`. — [mem0 docs: memory operations](https://docs.mem0.ai/core-concepts/memory-operations)
- April 2026 algorithm: "single-pass extraction" treating "agent-generated facts as first-class", and "multi-signal retrieval" fusing semantic similarity, keyword matching, and entity matching; graph support "replaced external graph stores with built-in entity linking (Neo4j/Kuzu still supported but not primary path)"; 20 vector stores (Qdrant, pgvector, Chroma, Redis, Elasticsearch, ...). Vendor-reported: LoCoMo 92.5 @ 6,956 tokens/query; LongMemEval 94.4 @ 6,787; BEAM-1M 64.1; BEAM-10M 48.6. Open problems listed by mem0 itself: temporal abstraction at scale, cross-session identity resolution, "memory staleness in high-relevance facts", privacy/consent. — [mem0 blog: State of AI Agent Memory 2026 (2026-10-26)](https://mem0.ai/blog/state-of-ai-agent-memory-2026)

**Zep / Graphiti**
- Paper (arXiv 2501.13956): Graphiti is a "temporally-aware knowledge graph engine" with episode, semantic-entity and community subgraphs; reports DMR 94.8% vs MemGPT 93.4%, and on LongMemEval "up to 18.5%" accuracy gain with 90% lower latency vs full-context baselines. — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956)
- Bi-temporal edge fields `valid_at`, `invalid_at`, `created_at`, `expired_at`; contradictions "automatically invalidate superseded edges while maintaining the temporal history"; hybrid retrieval = semantic embeddings + BM25 + graph traversal, optional cross-encoder rerank; custom entity/edge types via Pydantic; "Episodes represent raw ingested data—the ground truth stream. Every derived entity and relationship maintains provenance by tracing back to its source episodes." Backends: Neo4j 5.26+, FalkorDB 1.1.2+ (embedded "FalkorDB Lite"), Amazon Neptune, Kuzu (deprecated). Apache-2.0, ~32.4k stars; ships an MCP server and FastAPI service. — [getzep/graphiti README](https://github.com/getzep/graphiti)
- Invalidation mechanism: "an LLM invalidation prompt" compares new edges to existing ones; on contradiction the earlier edge (by `valid_at`) gets `expired_at` set and its fact text is regenerated (e.g., "Maria used to work as a junior manager, until her promotion"). `valid_at` is extracted by an LLM prompt given the episode reference timestamp; "our date extraction prompt emphasizes capturing only the information that can be derived from the context". Updates are incremental per episode, no batch recompute. — [Zep blog, 2024-10-02](https://www.getzep.com/blog/beyond-static-knowledge-graphs/)
- Valid time vs transaction time lets the system answer "What did the system know about X on date Y?" vs "What was actually true about X on date Y?" — [signals.aktagon.com summary (secondary)](https://signals.aktagon.com/articles/2026/07/zep-a-temporal-knowledge-graph-architecture-for-agent-memory/)

**Cognee**
- Storage: relational (SQLite, PostgreSQL) which "Tracks documents, chunks, and provenance (where data came from and how it's linked)"; vector (LanceDB, pgvector, Qdrant); graph (Kuzu, Neo4j, FalkorDB, Memgraph); can run "the whole memory layer on Postgres". v1.0 operations: Remember / Recall / Improve / Forget, over legacy `add` / `cognify` / `memify` / `search`. Search types include GRAPH_COMPLETION, CHUNKS, INSIGHTS, FEEDBACK; permissions, datasets and users supported; local-first mode with GLiNER extraction. Apache-2.0, ~33k stars. Claims BEAM 0.79 at 100K-token contexts (vendor-reported). — [topoteretes/cognee README](https://github.com/topoteretes/cognee); [Cognee docs core concepts](https://docs.cognee.ai/core-concepts)
- "DataPoints" are "structured data units that become graph nodes, carrying both content and metadata"; every graph node has a corresponding embedding so retrieval can move between similarity and traversal. — [Cognee docs](https://docs.cognee.ai/core-concepts); [cognee.ai blog](https://www.cognee.ai/blog/fundamentals/how-cognee-builds-ai-memory)

**LangMem (LangChain)**
- Semantic memory has two schemas: **Collections** (records that grow; "New information requires reconciling with existing memories through updating, consolidating, or deleting outdated entries"; "over-extraction reduces precision; under-extraction reduces recall") vs **Profiles** (single document; "Updates replace existing data"). Episodic = past experiences as few-shot examples; procedural = behavior rules refined via feedback (prompt optimizers). — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Two write policies: "Hot Path (Conscious)" — the LLM decides via `create_manage_memory_tool`/`create_search_memory_tool` during the turn (adds latency); "Background (Subconscious)" — `create_memory_store_manager` extracts after the turn ("Better for ensuring higher recall"). Update flags `enable_inserts`, `enable_deletes`, `enable_updates`. Storage is LangGraph `BaseStore` (InMemoryStore, AsyncPostgresStore) with hierarchical namespaces for org/user segmentation. — [LangMem docs](https://langchain-ai.github.io/langmem/); [conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)

**Hindsight (Vectorize; ACL 2026 demo)**
- Four networks: world (objective facts), experience, observation, opinion (subjective beliefs with confidence scores); operations retain / recall / reflect; retrieval = parallel vector + keyword + graph traversal + temporal filtering on PostgreSQL+pgvector; MIT license; reported LongMemEval 91.4% (Gemini-3 Pro) / 83.6% (20B OSS model), LoCoMo 83.2% (20B). — [ACL 2026 demo paper](https://aclanthology.org/2026.acl-demo.27/); [vectorize.io blog](https://vectorize.io/blog/introducing-hindsight-agent-memory-that-works-like-human-memory)

**Agent Zero Memory (arXiv, 2026-08-30)**
- "every learned item is a provenanced item carrying its origin, timestamp, and evidence pointer"; three stores: episodic event timeline, entity-event knowledge graph, and "Hierarchical Documentary Memory" that is "curated, citation-locked"; a "citation lock" means answers may only cite evidence the reader actually accessed, so the system abstains rather than fabricates. Reported LongMemEval 95.60%, LoCoMo 93.60%, "up to 20x lower per-query cost". — [arXiv 2608.29606](https://arxiv.org/pdf/2608.29606)

**Coding-agent memory designs**
- *Claude Code*: two systems — CLAUDE.md (human-written instructions; project/user/managed scopes; `@path` imports; `.claude/rules/*.md` with path-scoped loading; target "under 200 lines per CLAUDE.md") and **auto memory** (Claude-written). Auto memory stores four typed notes recorded as a `type` frontmatter field: `user`, `feedback`, `project`, `reference`. "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." Layout: `~/.claude/projects/<project>/memory/MEMORY.md` index (one line per memory) + topic files; "The first 200 lines of MEMORY.md, or the first 25KB ... are loaded at the start of every conversation"; topic files load on demand; over-limit writes return an error telling Claude to rewrite the index and "merge or drop stale entries". Writes stamp a `modified` ISO-8601 frontmatter field: "The timestamp shows how current the fact is". Scope is per git repo across worktrees, machine-local, not shared across machines. `/doctor prompt-audit` (v2.1.283+) finds "instructions written for older models, references to files or commands that don't exist, and files that contradict each other" and proposes edits without applying them. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- *Cursor*: project rules are `.cursor/rules/*.mdc` with frontmatter `alwaysApply`, `description`, `globs`; four modes (Always / Apply Intelligently / glob-attached / Manual `@`); AGENTS.md supported as a frontmatter-less alternative with nested directory scoping; Team Rules override project/user rules; keep rules "under 500 lines". — [Cursor docs: rules](https://cursor.com/docs/context/rules). The auto-generated **Memories** feature was removed in Cursor 2.1.x (2.1.17), with an "Export memories" command producing an `.mdc` to paste into Rules. — [Cursor forum](https://forum.cursor.com/t/are-my-memories-gone/144057); [forum thread 143744](https://forum.cursor.com/t/custom-modes-and-memories-gone-in-2-1/143744)
- *Cline memory bank*: six required markdown files in `memory-bank/` — `projectbrief.md` → `productContext.md`, `systemPatterns.md`, `techContext.md` → `activeContext.md`, `progress.md`; updated on discovering new patterns, after significant changes, or on the explicit command "update memory bank" (which requires reviewing ALL files); both humans and Cline edit them; "Cline's memory resets completely between sessions" so maintenance is manual. — [Cline docs: memory bank](https://docs.cline.bot/prompting/cline-memory-bank)
- *Aider repo map*: "a concise map of your whole git repository that includes the most important classes and functions along with their types and call signatures", built from tree-sitter symbols and ranked by "a graph ranking algorithm, computed on a graph where each source file is a node and edges connect files which have dependencies"; default budget `--map-tokens` 1,000, "adjusts the size of the repo map dynamically based on the state of the chat"; regenerated from current source each request (so never stale by construction). — [aider.chat repomap](https://aider.chat/docs/repomap.html)
- *AGENTS.md*: "A simple, open format for guiding coding agents"; plain markdown, no required fields; "the closest AGENTS.md to the edited file wins; explicit user chat prompts override everything"; originated with OpenAI Codex, Amp, Google Jules, Cursor, Factory; "stewarded by the Agentic AI Foundation under the Linux Foundation"; "Used by over 60k open-source projects"; 20+ tools. — [agents.md](https://agents.md/). Claude Code reads AGENTS.md only when no CLAUDE.md exists on the path, unless configured `claude-md-and-agents-md` (v2.1.277+). — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- *Codex CLI built-in memory* (third-party analysis of the open-source `codex-memory` crate, 2026-04-18): Phase 1 "Rollout Extraction" claims completed sessions from a SQLite state DB and makes parallel model calls producing raw memories + compact summaries; Phase 2 "Global Consolidation" runs serially, ranks stage-1 outputs by usage count and recency, "filters out stale memories exceeding the `max_unused_days` window, computes diffs (added/retained/removed)", and spawns a consolidation sub-agent with "no approvals, no network, and local write access only". Files under `~/.codex/memories/`: `MEMORY.md` (injected), `memory_summary.md`, `raw_memories.md`, `rollout_summaries/`, `skills/` ("learned procedural memories"), `memories_extensions/`. Config `generate_memories`/`use_memories` with per-phase model overrides; `/memories` TUI; not available in EEA/UK/CH; "Secret redaction is best-effort". — [codex.danielvaughan.com deep dive (secondary)](https://codex.danielvaughan.com/2026/04/18/codex-built-in-memory-system-deep-dive/); PR #16276 merged 2026-04-09 — [codex.danielvaughan.com (secondary)](https://codex.danielvaughan.com/2026/04/10/codex-cli-memory-extensions-cross-session-persistence/)
- *Karpathy "LLM knowledge base / LLM wiki" pattern (April 2026)*: three layers — immutable `raw/` sources, an LLM-compiled markdown wiki (summaries, entity pages, cross-references, contradiction flags), and a schema file (CLAUDE.md) describing how to operate; queries run against the wiki and answers are "filed back into the wiki"; periodic "health checks or linting" flag inconsistencies and gaps; Obsidian as the "IDE frontend". — [howaiworks.ai summary (2026-04-03)](https://howaiworks.ai/blog/andrej-karpathy-llm-knowledge-bases); [denser.ai summary](https://denser.ai/blog/llm-wiki-karpathy-knowledge-base/)

**Research systems / taxonomies**
- CoALA (Princeton, arXiv 2309.02427): working memory + long-term episodic, semantic, procedural (procedural = implicit in weights + explicit in agent code); "the standard reference for reasoning about agent memory architecture". — [arXiv 2309.02427](https://arxiv.org/pdf/2309.02427)
- "The Missing Knowledge Layer in Cognitive Architectures" (Roynard, 2026-04-13, rev. 06-12) argues CoALA/JEPA lack an explicit Knowledge layer and proposes four layers with different persistence semantics: Knowledge = "indefinite supersession", Memory = "Ebbinghaus decay", Wisdom = "evidence-gated revision", Intelligence = "ephemeral inference"; cites "BEAM benchmark's near-zero contradiction-resolution scores" and Karpathy's LLM KB as convergence evidence. — [arXiv 2604.11364](https://arxiv.org/pdf/2604.11364)
- A-MEM (NeurIPS 2025; arXiv 2502.12110 v8 2025-10-08): Zettelkasten-style notes with "contextual descriptions, keywords, and tags"; link generation against historical notes; "memory evolution" where new notes "trigger updates to the contextual representations and attributes of existing historical memories". — [arXiv 2502.12110](https://arxiv.org/abs/2502.12110)
- MemoryBank (arXiv 2305.10250, 2023-05-17): event summaries + user portrait, with "a memory updating mechanism, inspired by the Ebbinghaus Forgetting Curve theory" to forget/reinforce by elapsed time and importance. — [arXiv 2305.10250](https://arxiv.org/abs/2305.10250)

### Inferences
- The two coding-agent memories that are actually in production at scale (Claude Code, Codex) both chose **typed markdown + small always-loaded index + on-demand detail files + background consolidation**, not vector DBs. This is strong prior art that a markdown-in-git KB is adequate for engineering context.
- mem0's apparent move from UPDATE/DELETE (2025 paper) to ADD-only (2026 docs) suggests that LLM-driven in-place overwrite was unreliable or costly in production; the industry instead leans toward "never overwrite, mark superseded" (Graphiti bi-temporal, Roynard's "indefinite supersession", Agent Zero provenance).
- Letta's `read_only` shared blocks and MemFS git history are the closest OSS analogues to "verified, team-shared knowledge with an audit trail".
- Graphiti is the only mainstream OSS system with a formal valid-time/transaction-time model; everyone else approximates it with a single `modified`/`created_at` timestamp.

### Gaps
- I could not fetch Letta's current sleep-time agent configuration page or the MemFS layout page (404/ECONNRESET); exact MemFS file conventions (e.g., which files are always loaded) are unverified.
- Cognee's temporal-awareness and feedback-search internals were not fetchable in detail; only README-level claims were confirmed.
- mem0's memory `history` table (per-memory change log in SQLite) is known from older docs but was not confirmed on the current docs page I fetched; treat as uncertain for the 2026 version.

## Q2. Which approaches support human verification / correction and "confidence / verified" states?

### Takeaway
Explicit "verified" states are rare in OSS memory layers; what exists is (a) read-only / human-owned tiers (Letta `read_only` blocks; CLAUDE.md vs auto memory), (b) confidence-scored beliefs separated from facts (Hindsight opinions), (c) provenance + citation locks (Agent Zero), and (d) human review of proposed memory diffs before apply (Letta dreaming review mode, Claude Code `/doctor prompt-audit`, Codex consolidation diffs). None of the surveyed systems ships a first-class "human-verified fact" flag with expiry.

### Cited Findings
- Letta: `read_only: true` prevents agents from modifying a block, suggested for shared organizational memory. — [Letta docs: memory blocks](https://docs.letta.com/guides/agents/memory-blocks)
- Letta Code dreaming: "Select Agent reviews before applying to have your agent review and revise proposed memory updates in a second background conversation." — [Letta Code memory docs](https://docs.letta.com/letta-code/memory)
- Claude Code: human-authored CLAUDE.md vs Claude-authored auto memory are separate tiers; "Auto memory files are plain markdown you can edit or delete at any time"; `/doctor prompt-audit` reports findings "and nothing in your files changes until you ask Claude to apply them". — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Hindsight: "When an agent forms an opinion, the belief is stored separately from the supporting facts, accompanied by a confidence score"; world/experience/observation/opinion networks "separate objective facts from subjective beliefs". — [vectorize.io](https://vectorize.io/blog/introducing-hindsight-agent-memory-that-works-like-human-memory); [ACL 2026 demo](https://aclanthology.org/2026.acl-demo.27/)
- Agent Zero Memory: "citation lock" — answers may only reference evidence the reader actually accessed; items carry "origin, timestamp, and evidence pointer". — [arXiv 2608.29606](https://arxiv.org/pdf/2608.29606)
- Codex consolidation: "computes diffs (added/retained/removed)" and "The forgetting mechanism surfaces removed memories so the consolidation agent can make informed decisions"; users can toggle whether a thread contributes to memory. — [codex.danielvaughan.com (secondary)](https://codex.danielvaughan.com/2026/04/18/codex-built-in-memory-system-deep-dive/)
- Cline memory bank: "Both humans and Cline can access and modify these files." — [Cline docs](https://docs.cline.bot/prompting/cline-memory-bank)
- Cursor Team Rules "apply organization-wide from the dashboard and take precedence over project and user rules" (human-governed tier). — [Cursor docs](https://cursor.com/docs/context/rules)
- Roynard proposes "Wisdom: evidence-gated revision" as a distinct persistence class from facts. — [arXiv 2604.11364](https://arxiv.org/pdf/2604.11364)
- Hyperspell's failure-mode list recommends conflict resolution by "source authority, timestamp recency, explicit flags" and to "surface conflicts transparently". — [hyperspell.com (2026-06-24)](https://www.hyperspell.com/blog/memory-failure-modes)

### Inferences
- The cleanest OSS pattern for "verified" is **tiering by author** (human file vs agent file; read-only vs editable), plus **review-before-apply of diffs**. A per-item `status: proposed | verified | superseded` field with `verified_by`/`verified_at` is a natural extension none of these ship, but Claude Code's typed frontmatter and Letta's git commits show the plumbing is trivial in markdown.
- Hindsight's fact/belief split maps well to "business fact (verified)" vs "agent inference (unverified)" in a team KB.

### Gaps
- No surveyed OSS system documents a UI/API for a human to mark a memory as verified with an expiry; I found no reliable source for such a feature in mem0, Zep, or Cognee (Zep's hosted product may have fact-management UI, but I did not confirm).

## Q3. Anchoring knowledge to code versions / staleness detection — prior art

### Takeaway
Agent-memory products mostly use a single timestamp (plus "unused days" pruning); real code-anchoring prior art comes from documentation tooling (Swimm's code-coupled snippets/tokens/paths with auto-sync) and derived maps (Aider's repo map, which is recomputed from source and therefore never stale). Research (STALE benchmark, 2026) shows models are poor at noticing stale memories even when updated evidence is retrieved, so structural staleness detection must be done outside the model.

### Cited Findings
- Swimm couples docs to code via three element types — "Snippets", "Tokens" (identifiers such as function names), and "Paths" — and "verifies all code-coupled elements within your Swimm documents to match the latest source file updates"; docs are classified Up to date / Outdated (with auto-synced suggestions); users accept proposed updates, commit, and re-check status. — [Swimm docs: keep docs up to date](https://docs.swimm.io/ide-integrations/vs-code/ide-plugins-vscode-keep-docs-up-to-date); Swimm's GitHub App "alert[s] you to relevant documentation on PRs" when coupled code changes. — [Swimm blog](https://swimm.io/blog/how-swimms-github-app-works)
- Aider's repo map is regenerated from tree-sitter symbols each request, ranked by a dependency-graph algorithm, within a token budget. — [aider.chat repomap](https://aider.chat/docs/repomap.html)
- Claude Code stamps auto-memory files with a `modified` ISO-8601 time "so ... Claude when it reads the memory back" knows how current it is; it deliberately does not store "architecture, file paths, or debugging fixes" that can be re-derived from the codebase; `/doctor prompt-audit` finds "references to files or commands that don't exist". — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Codex consolidation "filters out stale memories exceeding the `max_unused_days` window". — [codex.danielvaughan.com (secondary)](https://codex.danielvaughan.com/2026/04/18/codex-built-in-memory-system-deep-dive/)
- Graphiti: bi-temporal edges; facts get `expired_at` when contradicted and the fact text is rewritten in past tense; valid-time extraction limited to "information that can be derived from the context" to avoid hallucinated dates. — [Zep blog](https://www.getzep.com/blog/beyond-static-knowledge-graphs/); [graphiti README](https://github.com/getzep/graphiti)
- STALE benchmark (arXiv 2605.06527): 400 expert-validated conflict scenarios / 1,200 queries across State Resolution, Premise Resistance, Implicit Policy Adaptation; "The best evaluated model achieved only 55.2% overall accuracy"; the gap is between retrieving updated evidence and acting on it; proposed CUPMem uses "structured state consolidation and propagation-aware search" and the authors argue "explicit state adjudication is a promising direction". — [arXiv 2605.06527](https://arxiv.org/abs/2605.06527)
- Hyperspell staleness mitigation: "Bi-temporal modeling tracking event time separately from ingestion time; reduced sync intervals; surface 'as of' timestamps in responses". — [hyperspell.com](https://www.hyperspell.com/blog/memory-failure-modes)
- "Ghost context": append-only memory lets "stale beliefs that never die" be "retrieved alongside their replacements". — [tianpan.co (2026-05-05)](https://tianpan.co/blog/2026-05-05-ghost-context-agent-memory-contradictory-beliefs)
- mem0 lists "Memory staleness in high-relevance facts" as an open problem. — [mem0 blog 2026-10-26](https://mem0.ai/blog/state-of-ai-agent-memory-2026)

### Inferences
- For `file@commit`-anchored code notes, the implementable prior art is Swimm's model: store the anchor as (path, symbol/token, snippet hash, commit); at check time run `git diff <commit>..HEAD -- <path>` and symbol lookup; classify as up-to-date / auto-resynced (path moved, symbol renamed but found) / outdated (snippet or symbol gone). This is cheap on git and needs no LLM.
- Combine two staleness signals, as Codex and Claude Code do: a *time* signal (`modified`, `last_used`, `max_unused_days`) and a *structural* signal (anchor validity). Because STALE shows models at ~55% on implicit conflicts, the KB should surface "anchor broken / superseded" flags explicitly rather than hoping the model notices.

### Gaps
- No agent-memory OSS project I found anchors memories to git commits natively; the closest are MemFS (memory itself versioned in git) and Codex's `max_unused_days`. Swimm's Auto-sync algorithm is patented and its internals are not public.

## Q4. Skill libraries: formats, auto-creation from experience, refinement loops, selection

### Takeaway
SKILL.md (folder + YAML frontmatter `name`/`description` + markdown body + optional `scripts/`, `references/`) has become the de facto cross-vendor format; auto-creation from trajectories is an active 2026 research area (SkillX, EvoSkills, SkillsVote, Ratchet, Procedural Graphs), but the strongest finding is that **lifecycle governance (eviction, capacity caps, authoring constraints) matters more than authoring**, and self-written skills without evaluation gates can be worth +0.0pp.

### Cited Findings
- Agent Skills format: "each skill is a folder with a SKILL.md file containing YAML front matter with at least name and description, plus instructions, along with optional scripts/, references/"; skills are "either auto-invoked (the agent detects when they are relevant) or user-invoked through slash commands". — [moltchat wiki summary of agentskills spec](https://moltchat-agent-commons.onrender.com/wiki/Agent_Skills_specification_(agentskills%2Fagentskills)); "Over 2,636 AI agent skills are now available across Claude Code, Codex, and OpenClaw". — [fungies.io](https://fungies.io/?p=36646)
- Claude Code's own guidance: if a CLAUDE.md entry "is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead". — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Codex memory writes "learned procedural memories" to a `skills/` directory as part of consolidation. — [codex.danielvaughan.com (secondary)](https://codex.danielvaughan.com/2026/04/18/codex-built-in-memory-system-deep-dive/)
- Letta Code documents "agent-owned skills" alongside MemFS. — [Letta Code memory docs](https://docs.letta.com/letta-code/memory)
- Voyager (2023-05-25): skill library stores behaviors "as executable code with searchable descriptions" (embedding of the description for retrieval), refined through "environment feedback, execution errors, and self-verification"; 3.3x more unique items, 2.3x longer distances, tech-tree milestones up to 15.3x faster; skills "generalize to novel Minecraft worlds". — [arXiv 2305.16291](https://arxiv.org/abs/2305.16291)
- SoK: Agentic Skills (2026-02-24): seven design patterns from "metadata-driven approaches to executable code skills, self-evolving libraries, and marketplace distribution"; lifecycle = discovery, practice, distillation, storage, composition, evaluation, updating; finds "curated skills improve agent performance while self-generated skills may reduce effectiveness"; documents the ClawHavoc campaign (~1,200 malicious skills in a marketplace). — [arXiv 2602.20867](https://arxiv.org/pdf/2602.20867)
- Ratchet (AWS/HSBC, arXiv 2605.22148 v3 2026-08-07): audit finds "LLM-written skills worth +0.0 percentage points against a no-skill control, human-written ones +16.2pp"; recipe = retirement by measured contribution (threshold −τ after N_min trials), fixed capacity C, meta-skill authoring guidance; on MBPP+/100 pass@1 0.258 → 0.658; eviction becomes inoperative when the LLM judge's false-pass rate ≥ (1−τ)/2. — [alphaxiv 2605.22148](https://www.alphaxiv.org/abs/2605.22148.md)
- SkillX (ICML 2026): distills trajectories into "hierarchical strategic plans, functional skills, and atomic skills", iteratively revises skills from execution feedback, and explores new skills. — [ICML 2026 listing](https://icml.cc/virtual/2026/82632); SkillsVote "admits only successful reusable discoveries to evidence-gated updates"; EvoSkills builds "multi-file skill packages". — [search summaries](https://www.emergentmind.com/papers/2605.18401)
- Procedural Graphs (arXiv 2609.09153, 2026-09-08, Google/Arik): procedures as "(procedure, relation, procedure) triplets"; an LLM refiner compares failed vs successful trajectories and edits the graph; edits that "preserve or improve held-out validation performance" are committed, rejected edits are retained to avoid repetition; at run time the surrounding subgraph becomes "step-level situational guidance". — [arXiv 2609.09153](https://arxiv.org/pdf/2609.09153)
- LangMem procedural memory = prompt rules refined by optimizers from feedback. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Cursor advice on when to write a rule: "Add rules only when you notice Agent making the same mistake repeatedly." — [Cursor docs](https://cursor.com/docs/context/rules)

### Inferences
- For a team KB, "playbooks" = SKILL.md-style folders selected by `description` match is the lowest-friction format and is portable across Claude Code, Codex and Cursor.
- Auto-drafting a playbook at ticket close is reasonable, but it should enter as `proposed` and only be promoted after human review or a measured success (Ratchet/SkillsVote evidence gating); otherwise expect library drift.

### Gaps
- No public numbers on how often Codex's auto-generated `skills/` are actually invoked or their quality; the Codex mechanism is from a third-party code reading, not OpenAI docs.

## Q5. Evidence of effectiveness (LoCoMo, LongMemEval, BEAM) and known failure modes

### Takeaway
Vendor-reported scores cluster at 92–96% on LoCoMo/LongMemEval (mem0 92.5/94.4, Agent Zero 93.6/95.6, Hindsight 91.4 LME), but independent audits show LoCoMo's answer key is ~6.4% wrong, the gpt-4o-mini judge accepts ~63% of deliberately wrong-but-topical answers, and reproduced LongMemEval scores can be ~20 points below published; BEAM at 10M tokens drops everyone to ~49% with contradiction resolution near-unsolved. Documented failure modes: staleness/ghost context, conflicting memories, pollution/over-retrieval, recursive summarization drift, and model failure to act on retrieved updates.

### Cited Findings
- LongMemEval (ICLR 2025): 500 questions over five abilities — information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention; "commercial chat assistants and long-context LLMs showing a 30% accuracy drop"; recommended designs: session decomposition, fact-augmented key expansion, time-aware query expansion. — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813)
- BEAM: 100 conversations of 100K–10M tokens, 2,000 questions over 10 abilities incl. contradiction resolution; "All models ... still struggle with contradiction resolution"; at 10M tokens the LIGHT framework shows +155.7% (Llama-4-Maverick) because no baseline supports full context. — [arXiv 2510.27246](https://arxiv.org/html/2510.27246v1)
- Reported scores (vendor/paper): mem0 LoCoMo 92.5 / LongMemEval 94.4 / BEAM-1M 64.1 / BEAM-10M 48.6 at ~7k tokens/query — [mem0 blog](https://mem0.ai/blog/state-of-ai-agent-memory-2026); Agent Zero LongMemEval 95.60, LoCoMo 93.60 — [arXiv 2608.29606](https://arxiv.org/pdf/2608.29606); Hindsight LongMemEval 91.4 (Gemini-3 Pro) — [ACL 2026 demo](https://aclanthology.org/2026.acl-demo.27/); Zep DMR 94.8 vs MemGPT 93.4 — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956); mem0 paper 26% relative over OpenAI memory, Mem0g +2% — [arXiv 2504.19413](https://arxiv.org/abs/2504.19413)
- Disputes: Zep claims that "when evaluated correctly on the same benchmark, Zep significantly outperforms Mem0" and that mem0's paper used "a demonstrably incorrect implementation of a competitor system (Zep)". — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/). Zep's LoCoMo score ranges from 58.44 (as measured by mem0) to 94.7 (by Zep) to 59–85 (third parties). — [braindetox.kr](https://braindetox.kr/en/posts/memory_benchmark_scores_reliability_2026.html)
- LoCoMo audit (2026-04-04): "6.4% of the answer key is wrong" (99 of 1,540 questions); the gpt-4o-mini judge "accepted 62.81%" of intentionally wrong, topically related answers; six requirements proposed (corpus beyond context window, adversarial judge validation, disclosed pipelines, verified ground truth). — [dev.to/penfieldlabs](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)
- Claimed vs observed (2026-07-28): mem0 LongMemEval "Published 93.4% | Observed 73.8%", gap attributed to "benchmark-specific prompt advantages" including "14 dataset-specific equivalence rules" and judge instructions to "lean toward yes". — [dev.to/gaurav_dadhich](https://dev.to/gaurav_dadhich/the-state-of-ai-memory-in-2026-claimed-vs-observed-1n94)
- Failure modes (Hyperspell, 2026-06-24): retrieval miss, ranking failure, staleness, permission block, conflict, assembly failure, utilization failure; mitigations: hybrid BM25+vector, cross-encoder rerank, bi-temporal modeling, conflict detection at ingest with resolution by "source authority, timestamp recency, explicit flags". — [hyperspell.com](https://www.hyperspell.com/blog/memory-failure-modes)
- "staleness, content pollution, conflicting memories, forgetfulness, and recursive ingestion drift from repeated summarization" named as core silent degraders; drift "only becoming visible in production deployments running six months or longer". — [conffab.com](https://conffab.com/presentation/your-agents-pass-every-benchmark-then-memory-breaks-them-in-production/); [aiweekly.co](https://aiweekly.co/alerts/ai-agent-memory-drift-goes-undetected-in-production)
- STALE: best model 55.2% on implicit conflicts; models "frequently accept outdated assumptions embedded in user queries". — [arXiv 2605.06527](https://arxiv.org/abs/2605.06527)
- Ratchet: unmanaged skill libraries cause "library drift" below the no-skill baseline. — [alphaxiv 2605.22148](https://www.alphaxiv.org/abs/2605.22148.md)
- LangMem documents the precision/recall tradeoff of extraction ("over-extraction reduces precision; under-extraction reduces recall"). — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Claude Code docs: "if two instructions contradict each other, Claude may pick one arbitrarily" and "Longer files consume more context and reduce adherence." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

### Inferences
- Benchmarks measure conversational recall, not engineering-KB usefulness; the absolute numbers should not drive architecture choice. The *qualitative* lessons are robust: hybrid lexical+vector retrieval beats either alone; time-aware queries matter; contradiction handling is the unsolved part; small, curated context beats large, noisy context.
- Over-retrieval and pollution are controlled in practice by hard context budgets (Claude Code 200 lines/25KB, Aider 1k tokens, mem0 ~7k tokens/query), not by smarter ranking alone.

### Gaps
- No published benchmark targets code-anchored or team-shared engineering knowledge; no independent reproduction of Agent Zero's or Hindsight's numbers was found.

## Q6. Practical recommendation for a small-team POC (SQLite + FTS5, markdown-in-git, Confluence publish)

### Takeaway
Adopt the coding-agent consensus (typed markdown notes, a tiny always-loaded index, on-demand detail, background distillation with human review of diffs, git as audit trail) plus two ideas from the graph-memory world (never overwrite — mark superseded with validity windows; store provenance pointers on every item) and Swimm-style structural anchors for code notes. Skip graph DBs, vector stores, and LLM-decided in-place UPDATE/DELETE for the POC.

### Cited Findings (patterns and their sources)
- Typed notes with frontmatter `type` and a `modified` timestamp; index capped at 200 lines/25KB; detail files loaded on demand; agent reminded to "merge or drop stale entries" when near the cap. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Two-phase background pipeline: per-session extraction (parallel, cheap model) → serial global consolidation that computes added/retained/removed diffs and prunes by `max_unused_days`. — [codex.danielvaughan.com (secondary)](https://codex.danielvaughan.com/2026/04/18/codex-built-in-memory-system-deep-dive/)
- Git-backed memory with one commit per edit and worktrees for concurrent background writers; optional "agent reviews before applying". — [Letta Code memory docs](https://docs.letta.com/letta-code/memory); [Letta MemFS (search snippet, unverified page)](https://docs.letta.com/letta-code/memfs)
- Read-only/human-owned tier vs agent-editable tier. — [Letta memory blocks](https://docs.letta.com/guides/agents/memory-blocks); [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Bi-temporal validity (`valid_at`, `invalid_at`, `created_at`, `expired_at`) and "invalidate, don't delete"; provenance from each fact to its source episode. — [graphiti README](https://github.com/getzep/graphiti); [Zep blog](https://www.getzep.com/blog/beyond-static-knowledge-graphs/)
- Provenance on every item: "origin, timestamp, and evidence pointer"; citation-locked answers. — [arXiv 2608.29606](https://arxiv.org/pdf/2608.29606)
- Collection vs Profile schemas: use replace-semantics only for single-state items; reconcile for growing collections. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Code-coupled anchors (snippet/token/path) checked against current source; statuses up-to-date / outdated; PR-time alerts. — [Swimm docs](https://docs.swimm.io/ide-integrations/vs-code/ide-plugins-vscode-keep-docs-up-to-date); [Swimm blog](https://swimm.io/blog/how-swimms-github-app-works)
- Don't store what can be re-derived from the repo (Claude Code skips architecture/file paths; Aider recomputes the repo map every request). — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [aider.chat](https://aider.chat/docs/repomap.html)
- Raw sources immutable + compiled wiki + schema file; answers filed back; periodic lint for contradictions. — [howaiworks.ai (Karpathy pattern)](https://howaiworks.ai/blog/andrej-karpathy-llm-knowledge-bases)
- Hybrid lexical + vector retrieval is the common mitigation for retrieval misses; mem0 fuses semantic + keyword + entity signals. — [hyperspell.com](https://www.hyperspell.com/blog/memory-failure-modes); [mem0 blog](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- SKILL.md folder format for playbooks; evidence-gated admission and retirement for auto-generated skills. — [agentskills spec summary](https://moltchat-agent-commons.onrender.com/wiki/Agent_Skills_specification_(agentskills%2Fagentskills)); [Ratchet](https://www.alphaxiv.org/abs/2605.22148.md)
- Nested AGENTS.md ("closest file wins") as the convention for directory-scoped context. — [agents.md](https://agents.md/)

### Inferences (recommendation)
**Worth adopting in the POC**
1. *Schema*: one markdown file per knowledge item with YAML frontmatter: `id`, `type` (business_fact | code_note | decision | service_contract | business_flow | playbook), `status` (proposed | verified | superseded | retired), `valid_from`, `valid_to`/`superseded_by`, `created_at`, `modified`, `last_used`, `sources[]` (ticket id, PR, Confluence URL, transcript span), `anchors[]` for code notes (`path`, `symbol`, `snippet_sha`, `commit`), `verified_by`/`verified_at`. Mirror the frontmatter into SQLite tables; FTS5 over title+body+tags. This is Claude Code's typed-note model plus Graphiti's validity window plus Agent Zero's provenance.
2. *Index + budget*: a generated `INDEX.md` (one line per verified item, capped like MEMORY.md) injected at ticket start, with full items fetched on demand by FTS5 query built from the ticket title/description plus touched paths. Budget tokens explicitly; do not inject everything.
3. *Write policy*: agent proposes items during work (hot path, `status: proposed`); a background "distill at ticket close" job (Codex phase-1 style) produces a diff of added/updated/superseded items; a human (or a second review pass, Letta-style) approves before `verified`. Never delete; set `superseded_by`.
4. *Staleness*: two cheap jobs — (a) structural: for each code_note anchor, check `git log -1 -- path` since `commit` and whether `symbol`/`snippet_sha` still exists → flag `outdated`; (b) temporal: items unused for N days or with `valid_to` passed → surface for review. Flag explicitly in the index line (e.g., `[STALE?]`), because models detect implicit conflicts poorly (STALE ~55%).
5. *Audit trail*: keep the KB in git (one commit per change, author = agent or human); Confluence is a publish target rendered from `verified` items only, with the git SHA and `sources` footer so readers can trace provenance.
6. *Playbooks*: SKILL.md-style folders; auto-drafts enter as proposed; promote only after a successful reuse or human sign-off; cap library size and retire unused ones (Ratchet).
7. *Lint*: periodic Karpathy-style health check prompt over the KB to flag contradictions and dangling anchors; output a report, do not auto-apply.

**Overkill for the POC**
- Graph databases / bi-temporal graph engines (Graphiti, Cognee, Neo4j): valuable semantics, but a `superseded_by` + validity columns in SQLite capture 90% of the benefit at team scale.
- Vector store / embeddings as the primary index: FTS5 with synonyms/tags plus title matching is adequate for a few thousand items; add embeddings later only if retrieval misses are observed.
- LLM-decided in-place UPDATE/DELETE of items (mem0 2025 style): mem0 itself moved to ADD-only in 2026; prefer supersession.
- Ebbinghaus-style decay scoring (MemoryBank) and A-MEM-style automatic note evolution: unnecessary churn for a curated, human-verified KB.
- Shared-block live sync across agents (Letta): git + review covers multi-user needs for a small team.

### Gaps
- No empirical data on retrieval quality for FTS5-only vs hybrid on engineering KBs; this must be measured in the POC.
- No OSS reference implementation of code-anchor staleness checking exists outside Swimm's proprietary product; the git-based check above is an inference from Swimm's documented model, not a tested design.
