# State, Tasks, HITL, Events/UI and LLM-gateway mechanisms in open-source agent orchestration (as of 2026-10-31)

Scope: LangGraph, Microsoft AutoGen / AG2 / Microsoft Agent Framework (MAF), CrewAI, MetaGPT, Temporal / Restate / Inngest AgentKit, AG-UI, ACP (Agent Client Protocol), MCP, A2A, LiteLLM, OpenRouter, Portkey, Bifrost. Research was done 2026-10-31 by fetching primary docs where possible; each finding carries its source. Where the doc page did not state a version/date, that is flagged.

## Key Question 1 — State: persistence, checkpoint schema, thread ids, crash resume, forks/time-travel, long human waits, context bounding

### Takeaway
Three distinct persistence models exist: (a) **checkpoint-per-superstep** (LangGraph, MAF) where a snapshot of all channels/executors + pending writes/requests is written at every step boundary and resume = reload latest checkpoint; (b) **journal/replay durable execution** (Temporal, Restate, Inngest) where the *code* is re-executed and completed side-effects are memoized, so waits for humans cost nothing and survive crashes; (c) **app-managed serialization** (AutoGen `save_state()` JSON dict, CrewAI `@persist` to SQLite keyed by state `id`) where the framework hands you a blob and you own storage. Only LangGraph documents a monotonically-increasing checkpoint id + parent pointer that gives native fork/time-travel; context bounding is explicit only in Temporal (hard 51,200-event / 50 MB history cap) and ACP (`compaction_update` events).

### Cited Findings

**LangGraph (checkpointers)**
- Checkpoint TypedDict fields: `v` (format version, currently `1`), `id` ("both unique and monotonically increasing, so can be used for sorting checkpoints from first to last"), `ts` (ISO 8601), `channel_values`, `channel_versions`, `versions_seen` ("Map from node ID to map from channel name to version seen"), `updated_channels`. — [LangGraph checkpoint base source](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py)
- CheckpointMetadata fields: `source` ∈ {`input`, `loop`, `update`, `fork`}, `step` (-1 for first input), `parents` (parent checkpoint ids by namespace), `run_id`, `counters_since_delta_snapshot`. CheckpointTuple = `config, checkpoint, metadata, parent_config, pending_writes`. — [same source](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py)
- Special pending-write slots: `WRITES_IDX_MAP` maps `ERROR: -1, SCHEDULED: -2, INTERRUPT: -3, RESUME: -4` — i.e., interrupts and resume values are stored as pending writes on the checkpoint. — [same source](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py)
- `BaseCheckpointSaver` interface: `get_tuple(config)`, `list(config, filter, before, limit)`, `put(config, checkpoint, metadata, new_versions)`, `put_writes(config, writes, task_id, task_path)`, `delete_thread(thread_id)`, plus async variants. Config keys: `thread_id` ("uniquely identifies a sequence of checkpoints"), `checkpoint_ns`, `checkpoint_id`. Default serializer `JsonPlusSerializer` ("ormsgpack with a fallback to extended JSON"); `EncryptedSerializer` wrapper for at-rest encryption. Backends: `InMemorySaver` (testing), `SqliteSaver`/`AsyncSqliteSaver` (lightweight/non-production), `PostgresSaver`/`AsyncPostgresSaver` (production). — [LangGraph checkpoints reference](https://reference.langchain.com/python/langgraph/checkpoints/)
- Durability modes passed as `durability=` on any execution call: `"exit"` (persist only when graph exits — success, error, or interrupt), `"sync"` (write every checkpoint before next step), `"async"` (write while next step runs; "small risk" of missing checkpoints on crash). "LangGraph creates a checkpoint at each super-step boundary." — [LangGraph durable execution docs](https://docs.langchain.com/oss/python/langgraph/durable-execution.md)
- Troubleshooting notes in the persistence page: `thread_id` must be under 255 chars for Postgres; in-memory checkpointers lose data on restart; "unbounded checkpoint accumulation" requires a pruning strategy; parent/subgraph state boundaries. Stores (cross-thread key-value) are separate from checkpointers. — [LangGraph persistence docs](https://docs.langchain.com/oss/python/langgraph/persistence)
- LangGraph Server (Platform/Studio backend) run status enum: `pending, running, error, success, timeout, interrupted`; thread status: `idle, busy, interrupted, error`; `multitask_strategy` for concurrent runs on one thread: `reject | interrupt | rollback | enqueue`. — [langgraph-sdk runs reference](https://reference.langchain.com/python/langgraph-sdk/_sync/runs); [langgraph-api Run model](https://docs.rs/langgraph-api/latest/langgraph_api/models/run/index.html)

**Microsoft Agent Framework (MAF) workflows**
- "Checkpoints are created at the end of each superstep ... A checkpoint captures the entire state of the workflow, including: the current state of all executors; all pending messages in the workflow for the next superstep; pending requests and responses; shared states." Python ≥ 1.13.0 also writes an entry checkpoint before the first superstep and when responses to request events are delivered, making "the complete workflow run replayable" (page dated 2026-09-16). — [MAF Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)
- Storage providers (Python): `InMemoryCheckpointStorage`, `FileCheckpointStorage` (explicit `storage_path`, no default), `CosmosCheckpointStorage` (partition key `/workflow_name`). Resume: `workflow.run(checkpoint_id=..., checkpoint_storage=..., stream=True)`; "A rehydrated workflow must preserve the topology and executor identities of the workflow that created the checkpoint." Built-in `AgentExecutorCheckpointState` has `cache`, `full_conversation`, `agent_session`, `pending_agent_requests`, `pending_responses_to_agent`. File/Cosmos stores use pickle with a restricted unpickler and `allowed_checkpoint_types`. — [MAF Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)

**AutoGen 0.4+ / AG2**
- AutoGen (0.4 line): agents and teams expose `save_state()` / `load_state()`; "State is a dictionary that can be serialized to a file or written to a database"; `AssistantAgent` state = its `model_context`; team `save_state` saves all member agents; custom agents default to empty state. — [AutoGen Managing State tutorial](https://microsoft.github.io/autogen/0.4.2/user-guide/agentchat-user-guide/tutorial/state.html)
- AG2's "resuming group chat" doc URL now redirects to `orchestration/group-chat/introduction/`; the resume mechanics could not be verified from a primary page in this pass (see Gaps). — [AG2 redirect](https://docs.ag2.ai/latest/docs/user-guide/advanced-concepts/resuming-group-chat/)

**CrewAI Flows**
- Flow state is either unstructured dict or Pydantic `BaseModel`; both auto-include a unique `id`. `@persist` (class- or method-level) saves state; default backend `SQLiteFlowPersistence`. Two hydration modes: `kickoff(inputs={"id": uuid})` resumes the existing flow; `kickoff(restore_from_state_id=uuid)` forks with a fresh state id. — [CrewAI Flows docs](https://docs.crewai.com/en/concepts/flows)
- Crew memory: short-term uses ChromaDB/RAG; long-term uses SQLite (`LTMSQLiteStorage(db_path=...)`) to store task results across sessions; entity memory uses RAG; storage locations resolved via `appdirs`. — [CrewAI Memory docs](https://docs.crewai.com/en/concepts/memory)

**Temporal**
- "The Workflow Execution's Event History is limited to 51,200 Events or 50 MB and will warn you after 10,240 Events or 10 MB." Default cap of 2,000 incomplete activities / child workflows / signals / cancellation requests; max 30 incomplete Nexus operations before Continue-As-New is needed. — [Temporal workflow execution limits](https://docs.temporal.io/workflow-execution/limits)
- Approval pattern: "Human-in-the-loop Workflows that block until external approval decisions are made. Uses Signals to capture approval data with metadata." Entity workflow pattern: "Signals and Updates driving every state transition." Integrations listed: OpenAI Agents SDK (Python/TS), LangGraph, Pydantic AI. — [Temporal AI docs](https://docs.temporal.io/ai)
- `workflow.wait_condition(fn, timeout=...)` returns when the condition is met or raises `asyncio.TimeoutError`; the condition "is only evaluated when the workflow state changes"; a workflow at `wait_condition` suspends with "no worker thread burning". Updatable/debounced timer pattern lets a Signal adjust a sleep. — [Temporal updatable timer pattern](https://docs.temporal.io/design-patterns/updatable-timer); [Temporal community thread](https://community.temporal.io/t/wait-condition-on-signal-execution-model/13527)

**Restate**
- "Restate replays the journal, skipping completed steps and resuming from exactly where it left off." Embedded K/V state for Virtual Objects and Workflows; "state updates are recorded alongside execution steps"; single-writer guarantee; concurrency limits for "expensive operations (like AI model calls)"; single Rust binary; SDKs for TS, Java, Kotlin, Python, Go, Rust, Ruby. — [Restate durable execution concepts](https://docs.restate.dev/concepts/durable_execution)
- "Each Virtual Object instance maintains isolated state and is identified by a unique key." Virtual objects "enforce session concurrency and queueing". — [Restate AI agents tour](https://docs.restate.dev/tour/ai-agents)

**Inngest AgentKit**
- Network State = message history (`InferenceResult` objects) + typed key-value data via `createState<T>()`. "The State's data is only retained for a single Network's run" — cross-run persistence must be implemented by the app. — [AgentKit State](https://agentkit.inngest.com/concepts/state)
- Network loop: router picks agent → agent runs (with tools) → result stored in State → router decides next or stop; `maxIter` guards loops; `defaultState` can seed state from external data. — [AgentKit Networks](https://agentkit.inngest.com/concepts/networks)

**MetaGPT**
- Global shared message pool with publish-subscribe; roles subscribe by interest ("the Architect mainly focuses on PRDs provided by the Product Manager"); agents "directly retrieve required information from the shared pool". Paper version v7, 1 Nov 2024 (ICLR 2024). — [MetaGPT paper v7](https://arxiv.org/html/2308.00352v7)

**Context bounding signals in protocols**
- ACP v1 session updates include `usage_update` (context window and cost), `compaction_update` (compaction started/ended) and `compaction_summary_chunk`. — [ACP prompt turn](https://agentclientprotocol.com/protocol/prompt-turn)

### Inferences
- LangGraph's checkpoint = (thread_id, checkpoint_ns, checkpoint_id, parent, channel_values, pending_writes incl. INTERRUPT/RESUME slots) is the most directly transferable schema for a SQLite POC: one `checkpoints` row per step with a parent pointer gives fork/time-travel for free (`source="fork"` metadata) and interrupts become rows, not process state.
- MAF's "pending requests are part of the checkpoint and re-emitted on restore" and LangGraph's INTERRUPT pending-write are the same idea: **an interrupt is a first-class persisted record**, not a blocked coroutine. Journal systems (Temporal/Restate/Inngest) reach the same outcome differently: the wait itself is durable, so no "interrupt record" is needed, but you then need the runtime (Temporal server / Restate binary / Inngest) to own replay.
- Only Temporal publishes a hard history ceiling; for a ticket-centric platform the equivalent is "one run per stage + continue-as-new at stage boundary" so a ticket's history never accumulates into one unbounded thread.
- AutoGen/CrewAI/AgentKit leave cross-run storage to the app, so they are closer to "libraries you embed inside your own state machine" than to orchestrators that own state.

### Gaps
- Exact Postgres table layout for LangGraph (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`) was not confirmed from a primary page in this pass; only the Python TypedDicts and the saver interface were verified.
- AG2 (the 0.2 lineage) `GroupChatManager.resume` / `messages_to_string` mechanics: the doc URL redirected and was not re-fetched; treat AG2 persistence details as unverified.
- Restate journal size limits / retention and Inngest step-count limits were not found in the pages fetched.
- MAF checkpoint *storage schema* (fields inside a persisted checkpoint document) is not enumerated in the docs page beyond the AgentExecutor state keys.

## Key Question 2 — Tasks: task/plan models, status models, dependencies, parallelism, retries, idempotency

### Takeaway
"Task" means very different things: CrewAI has an explicit `Task` object with `context` dependencies, `async_execution`, guardrails and `guardrail_max_retries`; MetaGPT's unit of work is a role-produced *document* (PRD → design → task list → code → test report) flowing through a pub/sub pool with a 3-retry executable-feedback loop; LangGraph/MAF have no task object — a "task" is a node/executor in a superstep, and idempotency is a requirement placed on the developer because nodes re-run on resume; A2A is the only protocol with a formal task state machine (`submitted → working → input-required/auth-required → completed/failed/canceled/rejected`), and ACP exposes a per-turn `plan` with entry `status` pending/in_progress/completed.

### Cited Findings
- CrewAI `Task` attributes: `description`, `expected_output`, `agent`, `context: List[Task]` ("prior task outputs for dependency management"), `async_execution` (default False), `human_input`, `output_json` / `output_pydantic` / `output_file`, `markdown`, `guardrail` / `guardrails` (sequential list), `guardrail_max_retries` (default 3), `tools`, `callback`, `name`, `config`. `TaskOutput`: `raw`, `json_dict`, `pydantic`, `agent`, `description`, `summary` (first 10 words), `output_format` ∈ {RAW, JSON, Pydantic}. Process types: sequential, hierarchical. Guardrail functions return `(bool, Any)`; string guardrails use the agent's LLM to validate. — [CrewAI Tasks docs](https://docs.crewai.com/en/concepts/tasks)
- CrewAI Flow control: `@start()` (incl. gated `@start("label")`), `@listen(method)`, `@router()` returning `Literal` route labels, `or_()` / `and_()` combinators for fan-in. — [CrewAI Flows docs](https://docs.crewai.com/en/concepts/flows)
- MetaGPT roles and artifacts: Product Manager → PRD (requirements, user stories, competitive analysis); Architect → system design (file lists, data structures, interface definitions); Project Manager → task decomposition; Engineer → code; QA Engineer → unit tests/review. Agents "communicate through documents and diagrams (structured outputs) rather than dialogue". Executable feedback: Engineer writes and runs unit tests, "debugging iterates up to 3 retries". Benchmarks: HumanEval 85.9% Pass@1, MBPP 87.7%, SoftwareDev executability 3.75, 0.83 human revision cost, 124.3 tokens/code line. — [MetaGPT paper v7](https://arxiv.org/html/2308.00352v7)
- LangGraph: "the node restarts from the beginning of the node where the interrupt was called when resumed, so any code before the interrupt runs again" → "Side effects before `interrupt()` should be idempotent". Nested subgraphs: both parent and child nodes restart. — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- MAF: "If an agent or executor fails, the runtime restarts that node from its checkpoint without re-running completed steps. This makes recovery deterministic and idempotent". — [Microsoft Tech Community post on Agent Framework](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/-/4460342)
- Inngest AgentKit router: `defaultRouter` gets `lastResult` and `callCount`, returns next agent or `undefined`; `maxIter` prevents infinite loops. — [AgentKit Networks](https://agentkit.inngest.com/concepts/networks)
- Restate: "Automatic retries with exponential backoff"; "Deduplication via idempotency keys"; concurrency limits per service. — [Restate durable execution](https://docs.restate.dev/concepts/durable_execution)
- Temporal incomplete-operation caps (2,000 activities/child workflows/signals) bound parallel fan-out per workflow. — [Temporal limits](https://docs.temporal.io/workflow-execution/limits)
- A2A 1.0.0 `TaskState`: `SUBMITTED, WORKING, COMPLETED, FAILED, CANCELED, INPUT_REQUIRED, REJECTED, AUTH_REQUIRED, UNSPECIFIED`; terminal = COMPLETED, FAILED, CANCELED, REJECTED; INPUT_REQUIRED and AUTH_REQUIRED are "interrupted". Task object: `id`, `contextId`, `status`, `artifacts`, `history`, `metadata`. RPCs: SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask, SubscribeToTask, push-notification config CRUD, GetExtendedAgentCard. Streaming events: `TaskStatusUpdateEvent`, `TaskArtifactUpdateEvent` (with `append` / `lastChunk`). — [A2A specification](https://a2a-protocol.org/latest/specification/)
- ACP `plan` session update: entries `{content, priority: high|medium|low, status: pending|in_progress|completed}`. — [ACP prompt turn](https://agentclientprotocol.com/protocol/prompt-turn)
- LangGraph Server `multitask_strategy` (`reject`, `interrupt`, `rollback`, `enqueue`) is the documented concurrency rule for two runs hitting the same thread. — [langgraph-sdk runs](https://reference.langchain.com/python/langgraph-sdk/_sync/runs)

### Inferences
- For a ticket→stage state machine, A2A's TaskState is the closest off-the-shelf status vocabulary (it already has `input-required` as a non-terminal "waiting on human" state and `rejected` as a terminal gate outcome). ACP `plan` entries are a good *sub-task* vocabulary within a stage.
- CrewAI's `context` list + `async_execution` is a DAG-lite; MetaGPT's design is "artifacts as the dependency edges" — each stage consumes the previous stage's document. For a BA/DEV/QA pipeline the MetaGPT "document per role" model maps 1:1 to stage outputs stored as versioned artifacts.
- Every checkpoint-based framework pushes idempotency onto the node author; the journal-based ones (Restate/Temporal/Inngest) make each side-effect a memoized step. In a SQLite POC, the cheap equivalent is "every tool/LLM call gets a `(run_id, step_key)` row written before execution; on resume skip rows that already have a result."

### Gaps
- No framework I fetched documents a role-based *task assignment* model with status transitions other than A2A (protocol-level) and CrewAI's hierarchical process (manager agent delegates); CrewAI's hierarchical status model is not specified in the Tasks page.
- MetaGPT's current repo-level task schema (post-paper, e.g. `Message` fields, `Document` class) was not fetched; only the paper mechanics are cited.

## Key Question 3 — HITL: interrupt patterns, approval nodes, routing approvals to people/roles

### Takeaway
Three interrupt mechanisms recur: **exception-style pause** (LangGraph `interrupt()` → `__interrupt__` with an `id` → `Command(resume=...)`, node re-executes), **typed request/response ports** (MAF `ctx.request_info()` → `request_info` event with `request_id` → `workflow.run(responses={request_id: value})`, pending requests saved in checkpoint), and **durable promise/event wait** (Restate `ctx.awakeable()` → HTTP `POST /restate/awakeables/{id}/resolve`; Inngest `step.waitForEvent` with `match` field and timeout; Temporal signal + `wait_condition(timeout)`). None of the frameworks ships role-based routing — they all emit an id and leave "who gets asked" to the app (Slack/email/dashboard); ACP standardizes the *client-side* permission prompt (`session/request_permission` with `allow_once/allow_always/reject_once/reject_always`).

### Cited Findings
- LangGraph: `interrupt(value)` surfaces in `result["__interrupt__"]` (invoke) or `stream.interrupts` / `stream.interrupted` (`stream_events(version="v3")`); each interrupt has an `id`; resume with `Command(resume=value)` or, for several, `Command(resume={interrupt.id: answer, ...})`; "Command(resume=...) is the only Command pattern intended as input to invoke()/stream()". `interrupt(..., response_schema=PydanticModel)` validates resume values (requires `langgraph>=1.2.12`) and exposes `Interrupt.response_schema` as JSON Schema. Multiple interrupts in one node are matched "strictly index-based". Never wrap `interrupt()` in bare try/except. Static breakpoints: `interrupt_before=[...]`, `interrupt_after=[...]`, resume by invoking with `None`. Patterns: approval → `Command(goto="approve"/"reject")`; review/edit → resume with edited value; tool approval → `interrupt()` inside the tool function. — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- LangGraph durability `"exit"` mode persists on "a human in the loop interrupt" — interrupts always force a checkpoint write. — [LangGraph durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution.md)
- MAF (Python): executor calls `await ctx.request_info(request_data=..., response_type=int)`; workflow emits `WorkflowEvent` with `type == "request_info"` carrying `event.request_id` and `event.data`; the app resumes with `workflow.run(stream=True, responses={request_id: value})`; `@response_handler` methods are matched by type annotations of `original_request` and `response`. C#/Go use `RequestPort.Create<Req,Resp>("name")` and `RequestInfoEvent`. "Runs are not isolated; state is preserved across multiple calls to run." Tool approval in agent orchestrations emits the same `RequestInfoEvent` with `ToolApprovalRequestContent` (C#/Go) or `Content` with `type == "function_approval_request"` (Python). "When a checkpoint is created, pending requests are also saved as part of the checkpoint state. When you restore from a checkpoint, any pending requests will be re-emitted as RequestInfoEvent objects"; you can pass both `checkpoint_id` and `responses` to `workflow.run(...)`. Page dated 2026-07-16. — [MAF Human-in-the-loop](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)
- CrewAI: `Task.human_input=True` "requires human review before completion"; Flows `@human_feedback` decorator (v1.8.0+) pauses for feedback, optional `emit` routes to labeled listeners, returns `HumanFeedbackResult` with `feedback` and `output`; history in `self.human_feedback_history`. — [CrewAI Tasks](https://docs.crewai.com/en/concepts/tasks); [CrewAI Flows](https://docs.crewai.com/en/concepts/flows)
- Restate: `const approval = ctx.awakeable<T>()` returns `{id, promise}`; id is sent via a durable step, e.g. `await ctx.run('request-review', () => requestHumanReview(claim, approval.id))`; approver resolves via `POST /restate/awakeables/{id}/resolve` with a JSON body (example: `curl localhost:8080/restate/awakeables/sign_1M28aqY6ZfuwBmRnmyP/resolve --json 'true'`); timeouts: TS `approval.promise.orTimeout({hours: 3})`, Python `restate.select(approval=..., timeout=ctx.sleep(timedelta(hours=3)))`; "Timeouts are durable"; "The exact destination isn't prescribed by Restate". — [Restate HITL pattern](https://docs.restate.dev/ai/patterns/human-in-the-loop)
- Inngest: `step.waitForEvent({id, event, timeout: "7d", match: "data.invoiceId" | if: expr})` returns the event or `null` on timeout; "Inngest manages the wait without maintaining an active function process"; "An event name alone can match unrelated runs" — match on a stable id; one event can resume multiple runs. — [Inngest wait-for-event](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/wait-for-event)
- Temporal: signal carries approval + metadata; `wait_condition(fn, timeout=...)` for deadline-bounded approvals. — [Temporal AI](https://docs.temporal.io/ai); [Temporal community](https://community.temporal.io/t/wait-condition-on-signal-execution-model/13527)
- A2A: `input-required` "is useful when an agent needs clarification, an approval, an additional document, or a missing parameter"; `auth-required` is a separate interrupted state. — [A2A specification](https://a2a-protocol.org/latest/specification/)
- ACP: Agent → Client `session/request_permission` with `options[{optionId, kind}]`, kinds `allow_once, allow_always, reject_once, reject_always`; client answers with the selected `optionId` or `cancelled`. — [ACP overview](https://agentclientprotocol.com/protocol/overview); [ACP prompt turn](https://agentclientprotocol.com/protocol/prompt-turn)
- MCP 2026-07-28 revision: elicitation changed — `notifications/elicitation/complete` and `elicitationId` (added 2025-11-25) were removed; experimental Tasks moved to an official extension; new "Multi Round-Trip Requests" pattern replaces server-initiated requests. — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- AG-UI: `RunFinished` carries optional `outcome` (success / interrupt). — [AG-UI events](https://docs.ag-ui.com/concepts/events)

### Inferences
- The common denominator across LangGraph/MAF/Restate/Inngest is an **interrupt record with a stable id, a typed payload/schema, and a resume-by-id API** — the framework never knows the approver. Role routing therefore belongs in the platform: `interrupt(id, kind, required_role, payload, response_schema, expires_at)` → notification adapters (Telegram/web) → `resume(id, actor, decision)`.
- LangGraph's `response_schema` (JSON Schema on the interrupt) and MAF's typed `response_type` both point to validating the human's answer at the boundary; a Telegram inline-keyboard can be generated from that schema.
- The two resume semantics differ in what a POC must guarantee: node-restart (LangGraph/MAF nested) requires idempotent pre-interrupt side effects; promise-resume (Restate/Inngest/Temporal) requires that *every* side effect be a memoized step. In SQLite, the second is simpler to emulate (a `steps` table) if the stage body is written as explicit steps.
- A2A's `input-required` and `auth-required` are useful stage-level states for a ticket UI; ACP's `request_permission` is the right shape for *tool-level* gates inside a coding-agent session.

### Gaps
- No primary source documents role-based approval routing (e.g., "QA lead must approve") in any framework; LangGraph Platform / LangSmith "Agent Inbox"-style UIs were not fetched.
- AG2 `human_input_mode` (ALWAYS/TERMINATE/NEVER) semantics were not verified from a live page in this pass.
- Whether LangGraph's `interrupt_id` is stable across process restarts (vs recomputed per resume) is not stated in the fetched page.

## Key Question 4 — Events/UI: AG-UI event types and state snapshot/delta, ACP session updates and permissions, Kiro CLI ACP, Zed adapters

### Takeaway
AG-UI's canonical "17 event types" (5 lifecycle, 3 text, 4 tool, 3 state, 2 special — per CopilotKit's Nov 2025 post) has since grown: the current docs add Activity (`ActivitySnapshot/Delta`), Reasoning (`ReasoningStart/End`, `ReasoningMessageStart/Content/End`, `ReasoningEncryptedValue`), Subagent (`SubagentStarted/Finished/Error`), chunk conveniences and `MessagesSnapshot`, with `StateDelta`/`ActivityDelta` defined as RFC 6902 JSON Patch over a prior snapshot. ACP v1 is JSON-RPC over stdio with `session/update` notifications (`agent_message_chunk`, `tool_call`, `tool_call_update`, `plan`, `usage_update`, `compaction_update`, ...) and a client-side `session/request_permission`; Kiro CLI exposes it via `kiro-cli acp` with `loadSession: true`, sessions persisted as JSON metadata + JSONL event log, and no custom system prompt; Zed runs any ACP agent via `agent_servers` config and may forward its MCP servers.

### Cited Findings

**AG-UI**
- CopilotKit's post (3 Nov 2025) enumerates the 17: Lifecycle `RunStarted, RunFinished, RunError, StepStarted, StepFinished`; Text `TextMessageStart, TextMessageContent, TextMessageEnd`; Tool `ToolCallStart, ToolCallArgs, ToolCallEnd, ToolCallResult`; State `StateSnapshot, StateDelta, MessagesSnapshot`; Special `RawEvent, CustomEvent`; and names drafts for Activity, Reasoning, Meta and interrupt/branching lifecycle events. — [CopilotKit: 17 AG-UI event types](https://webflow.copilotkit.ai/blog/master-the-17-ag-ui-event-types-for-building-agents-the-right-way)
- Current docs: 8 categories, ~40 types. `RunStarted` carries `threadId`, `runId`; `RunFinished` optional `outcome` (success/interrupt); `RunError` has `message`, optional `code`; `StepStarted/StepFinished` keyed by `stepName`; `TextMessageStart` has `messageId`, `role`; `TextMessageContent.delta`; `TextMessageChunk` auto-expands to Start→Content→End; `ToolCallStart` has `toolCallId`, `toolCallName`; `ToolCallArgs.delta`; `ToolCallResult.content`; `ToolCallChunk`; `StateSnapshot` = "Complete state snapshot"; `StateDelta` = "JSON Patch operations (RFC 6902)"; `MessagesSnapshot`; `ActivitySnapshot` / `ActivityDelta` (RFC 6902); `ReasoningStart/End`, `ReasoningMessageStart/Content/End`, `ReasoningEncryptedValue`; `SubagentStarted/Finished/Error`; `Raw` ("Events originating from external systems"); `Custom`. Deprecated events "will be removed in version 1.0.0". — [AG-UI events docs](https://docs.ag-ui.com/concepts/events)
- AG-UI was announced by CopilotKit in May 2025. — [DEV Community comparison](https://dev.to/czmilo/a2a-vs-mcp-vs-ag-ui-1a03)

**ACP (Agent Client Protocol)**
- Transport: JSON-RPC 2.0 over stdio. Agent methods: `initialize`, `authenticate`, `session/new`, `session/load`, `session/prompt`, `session/cancel` (notification), `session/set_mode`. Client methods: `session/request_permission`, `fs/read_text_file`, `fs/write_text_file`, `terminal/create|output|kill|wait_for_exit|release`, `elicitation/create`. Capabilities: `loadSession`, `promptCapabilities`, `mcpCapabilities`, fs/terminal flags. Stop reasons: `end_turn, max_tokens, max_turn_requests, refusal, cancelled`. — [ACP overview](https://agentclientprotocol.com/protocol/overview)
- Protocol version v1. `session/update` → `sessionUpdate` kinds: `user_message_chunk, agent_message_chunk, agent_thought_chunk, tool_call, tool_call_update, plan, available_commands_update, current_mode_update, config_option_update, session_info_update, usage_update, notice, compaction_update, compaction_summary_chunk`. Tool call fields: `toolCallId, title, kind, status, content?, locations?, rawInput?, rawOutput?`. Cancellation: client sends `session/cancel`; agent must stop LLM requests, abort tools, flush pending updates, and return `stopReason: cancelled`. — [ACP prompt turn](https://agentclientprotocol.com/protocol/prompt-turn)
- Tool-call status enum is reported inconsistently across pages: overview lists `pending, in_progress, completed, failed`; prompt-turn page lists `pending, in_progress, completed, cancelled`. — [ACP overview](https://agentclientprotocol.com/protocol/overview) vs [ACP prompt turn](https://agentclientprotocol.com/protocol/prompt-turn)

**Kiro CLI**
- Start with `kiro-cli acp` (or `kiro-cli acp --agent my-agent`); JSON-RPC 2.0 over stdin/stdout. Supported: `initialize`, `session/new`, `session/load`, `session/prompt`, `session/cancel`, `session/set_mode`, `session/set_model` (CLI v2; CLI v3 uses `session/set_config_option`). Advertises `loadSession: true` and `image: true`. Sessions persist at `~/.kiro/sessions/cli/` as a metadata JSON + a JSONL event log. CLI v2 custom methods prefixed `_kiro.dev/` (slash commands, MCP OAuth notifications, server init events); v3 replaces these with negotiated extensions. Editor setup: JetBrains `~/.jetbrains/acp.json`; Zed `settings.json` type `custom`. Logging via `KIRO_LOG_LEVEL=debug`, `KIRO_CHAT_LOG_FILE`. Limitations: "No custom system prompts"; content-filtered responses return `stopReason: refusal`. — [Kiro CLI ACP docs](https://kiro.dev/docs/cli/acp/)
- Kiro custom agent config: `mcpServers` map in the agent JSON (`command`, `args`), `includeMcpJson`; `allowedTools` pre-approves tools (`*`, `@builtin`, `@server_name`, `@server/api_*`, wildcards like `r*`); by default Kiro "requires user confirmation for most operations". — [Kiro custom agents](https://kiro.dev/docs/cli/custom-agents)

**Zed**
- Zed "manages the thread interface while agents maintain their own runtime, authentication, and model selection"; agents run as separate processes over ACP. Gemini CLI and Claude Agent come from the ACP Registry; "an Anthropic API key configured for Zed Agent does not automatically configure Claude Agent". Custom agents: `agent_servers.<name> = {type: "custom", command, args, env}`. Debug via `dev: open acp logs`. — [Zed external agents](https://zed.dev/docs/ai/external-agents)

**A2A streaming (for cross-reference)**
- `SendStreamingMessage` / `SubscribeToTask` emit `TaskStatusUpdateEvent` and `TaskArtifactUpdateEvent` (`append`, `lastChunk`); push notifications POST `StreamResponse` payloads to registered webhooks. — [A2A specification](https://a2a-protocol.org/latest/specification/)

**MCP**
- Latest revision 2026-07-28 (fifth since Nov 2024): removes the `initialize`/`notifications/initialized` handshake (stateless, per-request version negotiation); requires `server/discover`; moves Tasks to an official extension; introduces Multi Round-Trip Requests. 2025-06-18 added structured tool output, elicitation, OAuth resource-server role, `MCP-Protocol-Version` header; 2025-11-25 added experimental tasks, URL-mode elicitation, JSON Schema 2020-12 default. — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

### Inferences
- A normalized event stream for Telegram + web can be built as a strict subset of AG-UI: `RUN_STARTED/FINISHED/ERROR`, `STEP_STARTED/FINISHED` (= stage transitions), `TEXT_MESSAGE_*`, `TOOL_CALL_*`, `STATE_SNAPSHOT` + `STATE_DELTA` (RFC 6902), plus `CUSTOM` for ticket-specific events (approval requested/resolved). Telegram needs only snapshot-level events; the web UI consumes deltas.
- ACP `session/update` kinds map cleanly onto AG-UI: `agent_message_chunk→TEXT_MESSAGE_CONTENT`, `agent_thought_chunk→REASONING_MESSAGE_CONTENT`, `tool_call/tool_call_update→TOOL_CALL_START/RESULT`, `plan→ACTIVITY_SNAPSHOT or CUSTOM`, `usage_update→CUSTOM(cost)`. An ACP→AG-UI translator is a thin, stateless mapping if the platform assigns `runId` per stage session.
- Because Kiro CLI has no custom system prompt and gates tools via its own `allowedTools`, stage-level instructions must go through steering/agent config files and prompt content, and tool approvals must be answered by the platform acting as the ACP *client* (`session/request_permission`) — which is exactly where role-based approval can be inserted.
- `session/load` + JSONL session logs in Kiro mean per-stage sessions can be resumed by id, but the durable truth should remain the platform's own event log (Kiro's files are local to the machine running the CLI).

- ACP tool-call status conflict (`failed` vs `cancelled`) could not be resolved from the schema page in this pass.

## Key Question 5 — LLM gateways: budgets/spend per key/team, virtual keys, header tagging for cost attribution, Anthropic `ANTHROPIC_BASE_URL` compatibility, caching, self-hosting footprint

### Takeaway
LiteLLM and Bifrost are the two self-hostable gateways with full governance in OSS: both issue virtual keys, enforce dollar budgets at key/team/customer levels with reset windows, record spend per request with tags/metadata, and serve the Anthropic Messages format so Claude Code or any Anthropic SDK can be pointed at them via `ANTHROPIC_BASE_URL` with a virtual key as the credential. Portkey's OSS gateway (MIT, port 8787) does routing/fallback/caching but its budget limits are enterprise/hosted-only; OpenRouter is hosted-only but offers management-API-created per-user keys with `limit` + `limit_reset` and an Anthropic-format `/api/v1/messages`.

### Cited Findings

**LiteLLM proxy**
- Budget hierarchy: global proxy (`litellm_settings.max_budget`, `budget_duration`), team (`/team/new`), team member (`max_budget_in_team`), internal user (`/user/new`), virtual key (`/key/generate`), per-model (`model_max_budget`), end-user/customer (`/budget/new`, keyed by request `user`). "If a key belongs to a team, only the team (and team-member) budgets are enforced; the key owner's personal budget does not apply." Fields: `max_budget` (USD), `budget_duration` ("30s", "30m", "30h", "30d"), `soft_budget` (enterprise), `temp_budget_increase` + `temp_budget_expiry`; rate limits `tpm_limit`, `rpm_limit`, `max_parallel_requests`, `model_rpm_limit`, `model_tpm_limit`. `/key/generate` accepts `team_id, user_id, max_budget, budget_duration, model_max_budget, tpm_limit, rpm_limit, ...`. Budget exceeded → HTTP 400 `ExceededBudget`. Budget reservation (pre-estimate) on by default; `fail_closed_budget_enforcement: true` checks DB each request; multi-instance via `coordination_redis`; reset check every 10 min; per-model `budget_reset_at` (v1.107.0+). "Every budget on this page is enforced against spend read from the database, so none of them cap anything on a DB-less deployment" (PostgreSQL required). — [LiteLLM users/budgets](https://docs.litellm.ai/docs/proxy/users)
- Spend attribution: per key, internal user, team, end-user (`user` param), and tags. Tags via request body `metadata.tags: ["jobID:...", "taskName:..."]`, header `x-litellm-spend-logs-metadata` (JSON), or key/team-level `metadata.tags` for auto-tagging. `LiteLLM_SpendLogs` columns include `api_key` (hashed), `user`, `team_id`, `end_user`, `model`, `api_base`, `spend`, `total_tokens`, `prompt_tokens`, `completion_tokens`, `request_tags`, `metadata`, `startTime`, `endTime`, `cache_hit`. Endpoints: `/spend/logs`, `/spend/logs/v2` (paginated, 10,000-row cap), `/global/spend/report` (by team/customer/key), `/user/daily/activity`, `/global/spend/reset`. — [LiteLLM cost tracking](https://docs.litellm.ai/docs/proxy/cost_tracking)
- `/v1/messages` implements the Anthropic Messages API across "all LiteLLM supported providers"; Anthropic SDK: `anthropic.Anthropic(base_url="http://0.0.0.0:4000", api_key="sk-<virtual-key>")`; streaming, tool use, prompt caching (`cache_creation_input_tokens`, `cache_read_input_tokens`), `thinking.budget_tokens`, `metadata` supported. — [LiteLLM /v1/messages](https://docs.litellm.ai/docs/anthropic_unified)
- Claude Code setup: `export ANTHROPIC_BASE_URL="http://localhost:4000"`, `export ANTHROPIC_AUTH_TOKEN="sk-<virtual-key>"` (optionally `ANTHROPIC_MODEL`), or `ANTHROPIC_CUSTOM_HEADERS="x-litellm-api-key: Bearer sk-..."`. — [LiteLLM Claude Code client setup](https://docs.litellm.ai/docs/proxy/client_setup/claude_code)

**Claude Code gateway contract (Anthropic docs)**
- A gateway provides: credentials ("the provider key stays server-side; developers hold gateway credentials instead"), usage tracking by developer/team, cost controls, audit logging, provider switching. Roll-out: issue each developer a gateway credential; distribute `ANTHROPIC_BASE_URL` + credential via managed settings. `allowedProviders: ["customEndpoint"]` pins Claude Code to the gateway (requires Claude Code v2.1.285+). While a gateway credential or `apiKeyHelper` is active, requests bypass the claude.ai subscription and are billed to the credential owner; gateways forwarding OAuth traffic must forward the `anthropic-beta` header. Anthropic "doesn't support routing Claude Code to non-Claude models through any gateway." — [Claude Code: Other LLM gateways](https://code.claude.com/docs/en/llm-gateway)

**Bifrost (Maxim)**
- Virtual keys accepted via `x-bf-vk` (`sk-bf-*`), `Authorization: Bearer sk-bf-*`, `x-api-key` (Anthropic style), `x-goog-api-key`, `api-key` (Azure). Hierarchy: VK → team → customer (exclusive ownership); independent budgets at all three levels "all checked together"; reset durations `1m, 1h, 1d, 1w, 1M, 1Q, 1Y`, calendar-aligned UTC optional; budget overrides; dollar limits (e.g., `10.50`). Rate limits token- and request-based (VK level). Deny-by-default provider/model access with `provider_configs`, regex model filters (RE2). Metadata: ≤50 key/value entries (values ≤512 chars) "copied into log entries for spend filtering without caller headers". Key status/expiry (expired → 403); per-key content-logging tri-state. — [Bifrost governance](https://docs.getbifrost.ai/features/governance)
- Self-host: `npx -y @maximhq/bifrost` or `docker run -p 8080:8080 maximhq/bifrost` (tags `v1.3.9`, `-amd64`, `-arm64`); default port 8080; config in SQLite (`config.db`) or PostgreSQL ≥16; `config.json` seeds/reconciles DB; `config_store.enabled: false` for file-only mode; request logs in `logs.db`; OpenAI-compatible `/v1/chat/completions`; fallbacks, load balancing, semantic caching mentioned. — [Bifrost setup](https://docs.getbifrost.ai/quickstart/gateway/setting-up)
- Claude Code: `ANTHROPIC_BASE_URL=http://localhost:8080/anthropic`, `ANTHROPIC_API_KEY=<bifrost virtual key>`; "Claude Code does not know a gateway exists"; translates to "23+ supported providers". (Vendor blog, not the docs page.) — [Maxim: Claude Code with Bifrost](https://www.getmaxim.ai/bifrost/blog/integrating-claude-code-with-bifrost-gateway)

**OpenRouter (hosted)**
- Management API (`/api/v1/keys` GET/POST/PATCH/DELETE by `{hash}`) creates per-user keys with `name`, `label`, `limit` (credits), `limit_reset` ∈ {`daily`, `weekly`, `monthly`, null}, `disabled`, `include_byok_in_limit`; usage fields `usage`, `usage_daily`, `usage_weekly`, `usage_monthly`, `byok_usage`. Management keys cannot call completion endpoints; expired keys → 401; workspace-scoped keys → 403 elsewhere. — [OpenRouter management keys](https://openrouter.ai/docs/features/provisioning-api-keys)
- Anthropic-compatible base URL `https://openrouter.ai/api` with `/api/v1/messages`; "Claude Code with OpenRouter is only guaranteed to work with the Anthropic first-party provider". — [Zuplo OpenRouter guide](https://zuplo.com/docs/ai-gateway/openrouter)

**Portkey**
- Budget limits: USD or token based (min $1 / 100 tokens); reset none / weekly (Sun 00:00 UTC) / monthly (1st 00:00 UTC); key auto-deactivates when exhausted; not retroactive; "cannot be edited" once set; "available exclusively to Portkey Enterprise customers and select Pro users"; unsupported models cost $0 and don't count. — [Portkey budget limits](https://portkey.ai/docs/product/ai-gateway/virtual-keys/budget-limits)

### Inferences
- For "agent never holds credentials": issue one gateway virtual key **per stage session** (or per ticket) and inject it into the agent process as `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_API_KEY` + `ANTHROPIC_BASE_URL`; the key carries `team_id`/metadata so spend lands on the ticket without the agent cooperating. LiteLLM (`/key/generate` with `metadata.tags`) and Bifrost (VK metadata ≤50 entries) both support this directly; OpenRouter can emulate with management-API keys + `limit`.
- Per-ticket attribution via headers is only possible when you control the HTTP client (LiteLLM `x-litellm-spend-logs-metadata`, Portkey `x-portkey-metadata`); for black-box CLIs like Claude Code / Kiro, Claude Code's `ANTHROPIC_CUSTOM_HEADERS` works, otherwise rely on key-level metadata.
- Footprint for a small POC: Bifrost (single binary/npx, SQLite default, port 8080) is lightest; LiteLLM needs PostgreSQL for any budget enforcement; Portkey OSS lacks budgets; OpenRouter avoids self-hosting but exposes credit limits only (no per-request tag reporting verified here).
- Kiro CLI's provider routing is not reported to honor `ANTHROPIC_BASE_URL` (it authenticates to AWS/Kiro), so the "gateway holds the key" pattern applies cleanly to Claude Code and SDK-based agents; for Kiro the equivalent control is budgeting at the AWS/Kiro account level (unverified, see Gaps).

## Key Question 6 — Lessons for a small Python/SQLite POC: patterns to adopt, patterns to avoid

### Takeaway
The patterns that survive across all mature systems are: **interrupt as a persisted record with id + typed schema + resume-by-id**, **checkpoint (or step journal) per superstep with a parent pointer**, **monotonic per-run event sequence feeding snapshot+RFC 6902 delta streams**, **explicit concurrency policy per thread/ticket** (LangGraph `multitask_strategy`, Restate keyed single-writer), and **gateway-issued virtual keys with metadata for cost attribution**. Avoid: in-memory-only state, unbounded single-thread histories, bare node re-execution with non-idempotent side effects, and pickle-based checkpoints.

### Cited Findings
- Interrupts persisted as pending writes (`INTERRUPT: -3`, `RESUME: -4`) on the checkpoint. — [LangGraph checkpoint base](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py)
- "When a checkpoint is created, pending requests are also saved as part of the checkpoint state ... re-emitted as RequestInfoEvent objects" on restore. — [MAF HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)
- Checkpoint `id` is "monotonically increasing"; metadata `source` includes `fork`; `parents` map. — [LangGraph checkpoint base](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py)
- `StateSnapshot` then `StateDelta` (RFC 6902) is the AG-UI state model; `RunStarted` carries `threadId` + `runId`. — [AG-UI events](https://docs.ag-ui.com/concepts/events)
- `multitask_strategy` ∈ {`reject`, `interrupt`, `rollback`, `enqueue`} for concurrent runs on a thread. — [langgraph-sdk runs](https://reference.langchain.com/python/langgraph-sdk/_sync/runs)
- Restate virtual objects: keyed, isolated state, "enforce session concurrency and queueing". — [Restate AI agents tour](https://docs.restate.dev/tour/ai-agents)
- Side effects before `interrupt()` must be idempotent because the node re-runs. — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Durable timeouts: Restate `ctx.sleep` inside `select`; Inngest `timeout: "7d"` returns `null`; Temporal `wait_condition(timeout)`. — [Restate HITL](https://docs.restate.dev/ai/patterns/human-in-the-loop); [Inngest wait-for-event](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/wait-for-event); [Temporal community](https://community.temporal.io/t/wait-condition-on-signal-execution-model/13527)
- Unbounded history is a hard failure mode: 51,200 events / 50 MB cap in Temporal; LangGraph warns about "unbounded checkpoint accumulation". — [Temporal limits](https://docs.temporal.io/workflow-execution/limits); [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- MAF File/Cosmos checkpoint stores rely on pickle with a restricted unpickler and an explicit `allowed_checkpoint_types` list; "Checkpoint storage is a trust boundary." — [MAF Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)
- Structured documents per role instead of dialogue reduce "cascading hallucinations"; executable feedback loop with up to 3 retries. — [MetaGPT paper v7](https://arxiv.org/html/2308.00352v7)
- Gateway credential model: "the provider key stays server-side; developers hold gateway credentials"; one credential per developer so "offboarding revokes one credential". — [Claude Code gateways](https://code.claude.com/docs/en/llm-gateway)
- Kiro session storage is a metadata JSON + JSONL event log per session; `session/load` supported. — [Kiro CLI ACP](https://kiro.dev/docs/cli/acp/)
- MCP 2026-07-28 moved Tasks to an extension and made the protocol stateless per request. — [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

### Inferences
- Minimal SQLite schema that mirrors the verified patterns: `tickets(id, stage, status[A2A-like], version)`, `runs(id, ticket_id, stage, session_id, status[pending|running|interrupted|success|error|timeout], parent_run_id)`, `checkpoints(run_id, seq, parent_seq, state_json, source[input|loop|update|fork])`, `steps(run_id, step_key, status, result_json, idempotency_key)` (journal for LLM/tool calls), `interrupts(id, run_id, kind, required_role, payload_json, response_schema_json, status, expires_at, resolved_by, resolved_at, response_json)`, `events(run_id, seq, type[AG-UI subset], payload_json)`, `llm_keys(run_id, gateway_key_id, metadata_json)`.
- Concurrency control: adopt "one active run per ticket" with a LangGraph-style policy column (`reject|enqueue|interrupt`) rather than optimistic retries; this is what both LangGraph Server and Restate virtual objects encode.
- Context bounding: make each stage its own run/session (Temporal "continue-as-new at a boundary"); carry forward only the stage artifact (MetaGPT document) plus a compact summary, and emit an AG-UI `CUSTOM`/ACP-style `compaction_update` event when you do so, so UIs can explain gaps.
- Keep checkpoint payloads JSON (as LangGraph's JsonPlus and Go MAF stores do); avoid pickle to sidestep the trust-boundary issue MAF documents.
- Treat ACP as the *agent transport* (Kiro/Claude Code/Codex adapters) and AG-UI as the *UI transport*; the platform is the ACP client, so it owns `request_permission` answers and can enforce role gates there without agent cooperation.

### Gaps
- No source provides a measured comparison of SQLite write throughput for per-superstep checkpoints vs. step journals; the recommendation above is design inference, not benchmark-backed.
- No framework documented a Telegram adapter; routing design is inferred from Restate's "Slack/email/dashboard" guidance and Claude Code's managed-settings rollout model.
